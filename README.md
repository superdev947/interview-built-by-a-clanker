# Agentic Personas Storefront — Debugging Assessment

Welcome! This is a monorepo storefront application for browsing and purchasing AI-powered "Agentic Personas." The app was recently working, but a series of bugs have been introduced across the stack. Your task is to find and fix them.

## Tech Stack

- **Monorepo**: Turborepo + pnpm workspaces
- **Frontend** (`apps/web`): React 19, TanStack Router, TanStack Query, Tailwind CSS v4
- **Backend** (`apps/api`): Fastify 5, JWT auth, in-memory database
- **Shared** (`packages/shared`): TypeScript types, Zod validation schemas

## Getting Started

```bash
pnpm install
pnpm build
pnpm dev
```

- Frontend: http://localhost:5173
- API: http://localhost:3001

## Your Task

There are bugs scattered throughout the frontend, backend, and shared packages. Some will be immediately obvious (build failures, runtime crashes), while others are more subtle (incorrect behavior, broken features).

Work through the application and fix as many issues as you can. We're evaluating:

- **Debugging approach** — How you identify and isolate problems
- **Code comprehension** — How quickly you orient yourself in an unfamiliar codebase
- **Quality of fixes** — Whether your solutions are correct and clean

Feel free to use any tools or techniques you'd normally use on the job.

## Architecture

```
┌─────────────────────────────┐        HTTP/JSON + Bearer JWT        ┌──────────────────────────────┐
│ apps/web  (Vite :5173)      │  ───────────────────────────────────▶ │ apps/api  (Fastify :3001)    │
│ React 19                    │                                       │ @fastify/cors, @fastify/jwt  │
│ TanStack Router (file-based)│ ◀───────────────────────────────────  │ routes/* → db.ts (in-memory) │
│ TanStack Query (cache)      │                                       │                              │
└──────────────┬──────────────┘                                       └──────────────┬───────────────┘
               │            imports types + Zod schemas                              │
               └──────────────────────▶ packages/shared ◀───────────────────────────┘
```

- **Build orchestration**: Turborepo (`turbo.json`) runs `build`, `typecheck`, and `lint` with `dependsOn: ["^build"]`, so `@acme/shared` is compiled to `dist/` before `api` and `web` use it. `@acme/shared` exports only `./dist/index.js`, so you must build it before either app can resolve it.
- **Shared package** (`packages/shared/src/schemas/*`): Zod schemas plus inferred types for `Persona`, `User`/auth, `CartItem`/`Cart`, and `Order`/checkout. The API validates request bodies with these schemas, and the web app uses the same types for responses.
- **API** (`apps/api/src`)
  - `db.ts` keeps all data in memory with `Map` stores (`personas`, `users`, `cartItems`, `favorites`, `orders`) and seeds 15 personas at startup. **All data is lost on restart.**
  - `app.ts` exports `buildApp()`, which registers CORS (origin `http://localhost:5173`), JWT, and the route plugins; `index.ts` just calls it and listens on :3001. Tests use the same factory with `app.inject()`.
  - `middleware/auth.ts` defines the `authenticate` preHandler. It always verifies the JWT and short-circuits with `401` on failure.
  - `routes/*.ts` holds one Fastify plugin per domain. `cart`, `favorites`, and `checkout` each add `authenticate` as a plugin-level `preHandler` hook.
- **Web** (`apps/web/src`)
  - `main.tsx` nests `QueryClientProvider`, then `AuthProvider`, then `RouterProvider`.
  - `lib/api.ts` is a thin `fetch` wrapper. It adds `Authorization: Bearer <token>` from `localStorage["auth_token"]` and throws `ApiError` on any non-2xx response.
  - `lib/auth.tsx` is a React context that holds `user` and `token`. On load, if a token exists, it calls `/auth/me` to restore the user.
  - `routes/*` are file-based routes. `routeTree.gen.ts` is generated by the TanStack Router Vite plugin, so don't edit it by hand.

## Key Flows

### 1. Browse and search (`routes/index.tsx`)
1. The URL search params (`q`, `specialty`, `tier`, `minPrice`, `maxPrice`, `sort`) are parsed by `validateSearch`.
2. `SearchBar` debounces input by 300 ms, and `FilterPanel` toggles specialty, tier, and sort. Both call `updateSearch`, which calls `navigate({search})`, so the URL is the source of truth.
3. `useQuery` calls `GET /personas?...`. `db.personas.search` filters by text, specialty, tier, and price, then sorts.
4. Results render as `PersonaCard` links to `/personas/$personaId`.

### 2. Registration and login (`routes/register.tsx`, `routes/login.tsx`, `lib/auth.tsx`)
1. The form posts to `/auth/register` or `/auth/login`. The API validates with Zod, hashes the password with a toy hash, and signs a JWT `{id,email}`.
2. `login(response)` saves the token to `localStorage`, then sets `token` and `user` in context.
3. On page reload, `AuthProvider` reads the token and calls `/auth/me` to restore the user. A 401 clears the token.
4. Logout removes the token from `localStorage`, clears the context state, and clears the TanStack Query cache.

### 3. Persona detail, cart, and favorites (`routes/personas/$personaId.tsx`)
1. `GET /personas/:id` loads the persona. `GET /favorites` gives the IDs used to compute `isFavorited`.
2. **Add to Cart** calls `POST /cart`. The API merges quantity into an existing line or creates `cart-N`, then invalidates the `["cart"]` query.
3. **Heart** toggles the favorite with `POST /favorites` or `DELETE /favorites/:id`, then invalidates `["favorites"]`.

### 4. Cart management (`routes/cart.tsx`, `components/CartItem.tsx`)
- `GET /cart` returns enriched items (each with its persona) and a server-computed `total`.
- `+` and `−` call `PUT /cart/:itemId`, **Remove** calls `DELETE /cart/:itemId`, and each invalidates `["cart"]`.
- The navbar badge (`__root.tsx`) shares the `["cart"]` query, so it updates whenever the cart changes.

### 5. Checkout (`routes/checkout.tsx`, `api/routes/checkout.ts`)
1. The page shows the cart summary and a name/email form.
2. `POST /checkout` validates the form, builds an `Order` from the user's cart entries, and stores it.
3. On success, the page shows a confirmation screen and invalidates `["cart"]`.

### Backend (`apps/api`)

#### Bug 2 - Every authenticated route returns 500 by default

| | |
|---|---|
| **Where** | `apps/api/src/middleware/auth.ts` |
| **What** | `ENFORCE_AUTH` defaults to `false`. When false, `authenticate()` returns early **without** calling `request.jwtVerify()`, so `request.user` is `null`. Every route handler then does `const { id } = request.user` and throws. |
| **Verify** | `curl -i http://localhost:3001/cart -H "Authorization: Bearer $TOKEN"` (API started *without* `ENFORCE_AUTH`) |
| **Expected** | `200 {"items":[],"total":0}` |
| **Actual** | `500 {"error":"Cannot destructure property 'id' of 'request.user' as it is null."}` - same for `/favorites` and `/checkout`. |
| **Fix** | Always call `await request.jwtVerify()` (the `ENFORCE_AUTH` bypass was removed). Missing/invalid tokens now get `401`. |

#### Bug 3 - `authenticate` doesn't stop the request after a 401

| | |
|---|---|
| **Where** | `apps/api/src/middleware/auth.ts` - the `catch` block calls `reply.code(401).send(...)` but does not `return reply`. |
| **What** | In Fastify hooks you must `return reply` (or `throw`) to short-circuit; otherwise the route handler still runs after the 401 has been sent. |
| **Verify** | Start with `ENFORCE_AUTH=true`, then `curl -i http://localhost:3001/cart -H "Authorization: Bearer garbage"` and watch the API console. |
| **Expected** | 401 and the handler never executes. |
| **Actual** | *Not reproducible on Fastify 5* (it stops after a reply is sent from an async hook; see REVIEW.md C1). On older versions: 401 is sent, but the handler still runs and logs `FST_ERR_REP_ALREADY_SENT` / "Reply was already sent" warnings. |
| **Fix** | `return reply.code(401).send({ error: "Unauthorized" })`. |

#### Bug 4 - `minPrice` filter is inverted

| | |
|---|---|
| **Where** | `apps/api/src/db.ts` -> `personas.search()` |
| **What** | Uses `p.price <= minPrice` instead of `>=`. |
| **Verify** | `curl -s "http://localhost:3001/personas?minPrice=80"` |
| **Expected** | 2 personas (`p-002` $89.99, `p-011` $99.99). |
| **Actual** | 13 personas - everything **under** $80. |
| **Fix** | `p.price >= minPrice`. |

#### Bug 5 - `/auth/login` response omits `username`

| | |
|---|---|
| **Where** | `apps/api/src/routes/auth.ts` (login handler) |
| **What** | Register returns `user: {id, email, username}`; login returns only `{id, email}`. The web `AuthProvider` stores this object, so the navbar greeting is blank after login (but not after register). |
| **Verify** | `curl -s -X POST http://localhost:3001/auth/login -H "Content-Type: application/json" -d '{"email":"a@b.com","password":"secret1"}'` |
| **Expected** | `"user":{"id":"...","email":"a@b.com","username":"alice"}` |
| **Actual** | `"user":{"id":"...","email":"a@b.com"}` |
| **Fix** | Include `username: user.username` in the login response. |

#### Bug 6 - Checkout never clears the cart

| | |
|---|---|
| **Where** | `apps/api/src/routes/checkout.ts` |
| **What** | An order is created, but `cart.clearForUser(userId)` (which exists in `db.ts`) is never called. Checking out again creates a duplicate order for the same items. |
| **Verify** | Run API with `ENFORCE_AUTH=true`, then:<br>`curl -s -X POST localhost:3001/cart -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"personaId":"p-001","quantity":1}'`<br>`curl -s -X POST localhost:3001/checkout -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"name":"Alice","email":"a@b.com"}'`<br>`curl -s localhost:3001/cart -H "Authorization: Bearer $TOKEN"` |
| **Expected** | Final `GET /cart` -> `{"items":[],"total":0}` |
| **Actual** | Cart still contains `p-001`; a second checkout creates a second order. |
| **Fix** | Call `cart.clearForUser(userId)` after creating the order. |

#### Bug 7 - CORS blocks `DELETE` from the browser

| | |
|---|---|
| **Where** | `apps/api/src/index.ts` (now `app.ts` on the fix branch) -> `@fastify/cors` `methods: ["GET","POST","PUT","OPTIONS"]` |
| **What** | `DELETE` is not in the allowed-methods list, so browser preflight fails for *Remove from cart* and *Unfavorite*. `curl` is unaffected (no preflight). |
| **Verify** | `curl -i -X OPTIONS http://localhost:3001/cart/x -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: DELETE"`<br>UI: add an item to the cart, click **Remove**, open DevTools -> Console. |
| **Expected** | `access-control-allow-methods` includes `DELETE`; item removed in UI. |
| **Actual** | `access-control-allow-methods: GET, POST, PUT, OPTIONS`; browser logs a CORS error and the item stays. |
| **Fix** | Add `"DELETE"` to `methods`. |

#### Bug 8 - Any user can delete any cart line (IDOR)

| | |
|---|---|
| **Where** | `apps/api/src/routes/cart.ts` -> `DELETE /cart/:itemId` |
| **What** | Handler looks the item up by id and deletes it without checking `item.userId === request.user.id`. |
| **Verify** | With `ENFORCE_AUTH=true`: register two users (TOKEN_A, TOKEN_B). As A, `POST /cart` and note the returned item `id`. As B: `curl -i -X DELETE localhost:3001/cart/<A's item id> -H "Authorization: Bearer $TOKEN_B"`. Then `GET /cart` as A. |
| **Expected** | B gets 404/403; A's cart unchanged. |
| **Actual** | B gets 200/204; A's cart is empty. |
| **Fix** | Return 404 when `item.userId !== userId`. |

#### Bug 9 - `POST /favorites` body is not validated

| | |
|---|---|
| **Where** | `apps/api/src/routes/favorites.ts` |
| **What** | Other routes parse the body with Zod; favorites casts `request.body` and only checks truthiness, so a wrong-typed `personaId` (e.g. a number) slips past validation and is treated as an unknown persona. |
| **Verify** | `curl -i -X POST localhost:3001/favorites -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"personaId":123}'` |
| **Expected** | 400 with a validation error. |
| **Actual** | `404 Persona not found` - the type error is never reported. |
| **Fix** | Added `addFavoriteSchema` (`{ personaId: z.string().min(1) }`) to `@acme/shared` and `safeParse` it in the route. |

#### Bug 17 - Web client sends `Content-Type: application/json` on body-less requests

### Security notes (not assessment "bugs", but worth knowing)

- JWT secret is hard-coded (`agentic-personas-dev-secret`) in `apps/api/src/app.ts` - should come from an env var.
- Passwords are hashed with a toy 32-bit string hash in `apps/api/src/routes/auth.ts` - use `bcrypt`/`argon2`.
- The token lives in `localStorage` - susceptible to XSS exfiltration; prefer an `httpOnly` cookie.
